RLM Harnesses and Compositional Generalization: What FDEs Should Test

Understand harness compositional generalization, surrogate training and RLM-27B, then test whether decomposition preserves correctness, context and total execution cost.

BY ARJUN MEHTA · FDEINTERVIEWS EDITORIAL · UPDATED NOVEMBER 25, 2026 · 4 MIN READ

PRACTICE THIS:Study harness engineering ·Diagnose long agent loops ·Understand agent training targets

A recursive language model harness can move large inputs out of the prompt, let an agent inspect selected portions through code, and delegate bounded subproblems. Compositional generalization asks whether those parts combine correctly on tasks unlike the training examples. Smaller prompts alone do not establish that property.

The November 2026 paper Language Model Harnesses can be Compositional Generalizers, by Alex L. Zhang, Souradip Chakraborty and Omar Khattab, investigates this question. For a forward deployed engineer, it suggests a more useful experiment than simply increasing the context window: test the decomposition, the information passed between calls and the final merge.

What the research establishes

The authors study harnesses that keep individual model calls locally similar to familiar tasks while composing them into larger work. Their synthetic experiments show generalization to tasks 2–64 times longer under the studied conditions. They also construct surrogate environments with inexpensive or simulated tool and subcall responses to teach useful decomposition behavior. These results do not guarantee transfer to arbitrary workflows. Paper.

The released repository distinguishes RL experiments from RLM-27B, trained with synthetic-environment supervised fine-tuning. Its release includes experiment configurations, trajectory logs and model links. We inspected those materials; we did not train the checkpoint or rerun its GPU evaluation.

In Table 4, the Qwen3.8-27B base model in an RLM harness averages 46.1 across eight benchmarks; RLM-27B reaches 58.5. That is 12.4 points, approximately 26.9% relative. Table 5's rounded root-plus-child token counts sum to roughly 721K versus 385K per trajectory. This supports an approximately twofold token reduction in that comparison, not a universal latency claim. Tables 4–5.

Define a decomposition contract

Suppose a customer asks for the number of distinct accounts with an unresolved incident across several regional exports. A planner splits the files by region. Each worker counts its accounts and returns a number. Every local answer can be correct while the total is wrong: the same account appears in several regions.

The contract should instead define what each worker returns and how the coordinator combines it. For this example, workers return canonical account identifiers with evidence references; the coordinator unions those identifiers before counting. A separate normalization step must establish when two identifiers refer to the same account.

This is an original teaching example, not the paper's benchmark architecture. The essential property is visible: the intermediate representation retains the information required by the merge. Compression that discards account identity prevents a correct global distinct count.

The same reasoning applies to evidence review. If two contracts define an exception and a general rule, independent summaries may discard their relationship. If one log contains the request and another its eventual commit, splitting by file can hide the causal connection. Test those dependencies before treating a task as safely parallel.

Run a small counterexample

This standard-library Python example needs no model. Predict the incorrect total and the correct answer first.

python
regions = [{"a", "b"}, {"b", "c"}, set()]

def merged_accounts(parts):
    result = set()
    for part in parts:
        result.update(part)
    return result

local_sum = sum(len(part) for part in regions)
combined = merged_accounts(regions)
assert local_sum == 4
assert combined == {"a", "b", "c"}
assert merged_accounts([]) == set()
assert merged_accounts(reversed(regions)) == combined
assert merged_accounts(regions + regions) == combined
print("sum of local counts:", local_sum)
print("global distinct count:", len(combined))

The output is four versus three. The assertions check empty input, partition order and duplicate delivery. They establish properties of this reducer, not the reliability of a language model that extracts the sets.

Next, introduce conflicting identifiers or a worker that silently omits an account. The reducer cannot repair missing evidence. You need separate checks for extraction completeness, identity normalization and composition. This is why a single end-to-end score is insufficient for diagnosing failures even when it is the right release metric.

Measure the full execution tree

Our long-horizon agent exercise covers repeated actions and stopping conditions. A decomposition experiment needs those controls plus an explicit cost ledger:

MeasurementIncludeWhat it helps distinguish
Task correctnessFinal answer and supporting evidenceUseful completion versus plausible intermediate work
Context exposureRoot inputs and each child's inputsSmaller local problems versus merely hidden context
Total tokensRoot, children, repair calls and retriesActual work versus a short visible transcript
LatencyQueueing, parallel branches and slowest required branchToken savings versus customer waiting time
Failure behaviorTimeout, recursion depth and incomplete child resultsA recoverable partial result versus silent omission

This proposed experiment changes one component at a time. Start with the same model, input set and total budget. Compare a direct baseline with a decomposition harness, then evaluate any trained policy separately. Record root and child model identities; changing one is an additional intervention.

For training, distinguish environment observations from model-produced actions. The agent training loss-mask concept explains why that distinction matters. A trace containing the right answer does not automatically constitute the right learning target.

Decide when decomposition earns its complexity

A good first customer task has a checkable merge, bounded subtasks and enough repeated structure to justify learning or scripting the decomposition. A poor first task depends on subtle global interactions that your intermediate format cannot preserve.

Use a deliberately longer holdout and at least one new input structure. Include a cross-boundary dependency, an empty branch and an unavailable child. Require the system to disclose incomplete work instead of confidently merging whatever returned. Keep the evaluation set outside the optimization loop, as in our self-improving harness review.

The handover should explain which transformations preserve correctness and which remain empirical model behavior. Work through the harness engineering course to connect that reasoning to runtime limits and recovery. The useful deployment result is a task that remains correct as its size changes, with enough evidence to explain both its successes and its failures.
