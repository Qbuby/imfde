Común：13 人工程团队如何将产出增至三倍

后端 PR 数量从每周 50 个增至 170 个，4 周内实现 3 倍产出。

新产品开发速度提升 2–3 倍，从 10 周缩短至 4 周。

82% 的后端 PR 由 Devin 撰写，此前占比 18%。

Común 是面向美国拉丁裔侨民的支付网络。用户可在美或 17 个拉美国家收付款、消费。行业：金融科技。

Común 围绕拉丁裔移民的资金流动习惯设计金融服务。传统机构常要求现金汇款支付高额手续费、开户需到网点并提交美国生活文件。Común 平台去除了这些障碍：支持 100 多种拉美身份证明开户、向 17 个拉美国家提供直达银行或现金取款、美国境内零售店和 ATM 存现金、ComúnPay 可向美国任何人转账。

13 人工程团队无法同时完成所有路线图：快速上线 WhatsApp 通道、重构纠纷流程、大力推进稳定币、为 App 和网页产品嵌入 AI 助手。

两点认识让 Común 转向后台代理：工程师每天需不断引导本地代理处理 PR 评论、补充上下文、跟踪任务，限制了每人可同时运行的代理数量；每位工程师都在本地孤立地构建 AI 工作流，包含个人记忆、本地自动化和产品上下文。集中平台可让所有人的改进即时共享。

Común 曾在一年前尝试 Devin，当时产品尚早，未在内部推广。之后尝试自建后台代理，但决定把精力放在产品和平台建设上：自定义 MCP 服务器、更快 CI、带种子数据的端到端测试、通过 Devin 运行的 Android 模拟器、自定义 lint 规则，以及“微审查器”——每 PR 约 20 项 AI 检查，强制执行 Común 代码库的特定模式。

再次使用 Devin 时，Devin 可端到端完成任务：理解代码库、编写代码、运行并测试应用、自检、提交 PR 供人工审查。

“使用 Devin 的体验很神奇，它能从端到端测试角度理解工程师需求，把 PR 推进到可供人工审查的程度。”——Luis，工程与数据负责人

Común 先把 Devin 用于新产品项目，并自建名为 Swarm 的内部编排工具。Swarm 将 Linear 项目视为工单的有向无环图。工程师一次规划多达 20 个工单，根据 DAG 选择委托给 Devin 的任务，发送后台运行，所有会话集中查看。

会话在后台持续，工程师可通过手机跟进，关机后仍让代理工作。每个 PR 上，Devin 和微审查器迭代直至完成，人工只做最终审查。

使用量上升后的 4 周内，后端团队 PR 量从每周 50 个增至 170 个，实现 3 倍增长，同时交付 WhatsApp 上线和纠纷重构。Devin 创建的后端 PR 占比从 18% 升至 82%。

稳定币团队把整个项目拆成可由 Devin 代理舰队执行的明确任务，计划就绪后即可执行。Común 预计将原 10 周周期压缩 2–3 倍至 4 周。

Común 给 Devin 提供与工程师相同上下文：排除个人身份信息的数据库、Datadog 日志、功能开关、通过自定义 API 接入的外部供应商数据。Devin 自动接收 Slack 告警、调查，常带修复方案返回。告警为噪音时，Devin 告知工程师无需操作。支持代理的升级同样处理。

每周每队“守门员”曾整轮处理告警和升级，现在可做基础修复。低优先级技术债和小性能改进也能完成，因为任何人均可从 Slack 派 Devin 代理调查修复。

Analytics 让 Devin 访问自身 dbt 环境，使其成为增长、运营和产品团队可直接使用的数据平台。产品经理发现问题可请 Devin 调查并推送修复，工程师验证合并。数据科学团队正探索用 Devin 训练机器学习模型和运行日常工作流，Devin 即将能端到端运行和测试 Común 移动应用。

Devin 让 Común 以精简团队追求更多目标。稳定币和 App 内 AI 助手均在推进，招聘重点转向具备强判断力和系统设计能力、能跨基础设施、后端、前端编排多代理的工程师。

“我们对 Devin 设置、验证循环、数据上下文的每一次小更新，都能节省数小时调查、代码审查或执行时间。作为公司，我们正尝试在增加人员、流程、结构之前，先弄清边界在哪里。”——Luis，工程与数据负责人

给负责人

要解决什么
13 人工程团队需要上线 WhatsApp、彻底改造争议处理、推进稳定币，并构建应用内 AI 助手，同时不能按路线图规模招人。
结果
使用量起飞后的四周内，后端 PR 从平均 50/周升至 170（3x）。由 Devin 创建的后端 PR 占比从 18% 升至 82%。页面主视觉还写到新产品估计 2–3x 加速，从 10 周到 4 周（稳定币团队正在为智能体集群结构化工作；预期）。
接了哪些系统
内部编排工具 Swarm；Slack 告警页；通过 Devin 使用 Android 模拟器；自定义 MCP 服务器；微型审查者（每个 PR 约 20 项 AI 检查）。
用了什么数据
Linear 项目；不含 PII 的数据库；Datadog 日志；功能开关；供应商 API；dbt 环境。
人还管哪一步
人聚焦最终 PR 审查；产品经理请 Devin 调查/修复，由工程师验证并合并。
多久上线
使用量起飞按四周衡量。稳定币项目在计划就绪后预期从 10 周到 4 周（2–3x）——预期，尚未完成。

给现场的人

主要用在哪
通过 Swarm 交付新产品（把 Linear DAG 中的工单委派给 Devin）；Slack 值班/分诊；非工程人员通过 analytics dbt 访问。
以前怎么干
工程师花数天引导本地智能体（PR 评论、后续上下文）。每位工程师各自构建隔离的本地 AI 工作流。一年前首次试用 Devin 没有形成采用；团队随后尝试自建后台智能体。
卡在哪
本地智能体的开销限制了每位工程师能运行的智能体数量；改进停留在个人机器上。
用了什么模型
Devin
事情怎么流转
工程师界定工单范围（有时 20 个），从 DAG 中选择委派哪些，发给后台 Devin。Devin + 微型审查者迭代，直到人工终审。值班：Devin 接手 Slack 告警页、调查，常常带着修复方案到来，或说明无需操作。
怎么验收
每周后端 PR 数量；由 Devin 撰写的后端 PR 占比。
怎么上线
13 人工程团队；工程师用手机跟进；机器关闭后会话仍继续运行。
失败了怎么改
约 1 年前首次尝试 Devin 没有形成采用。自研后台智能体被放弃，以便团队把精力花在产品和智能体平台工作上。
能不能复用到下一家
Swarm 编排器；微型审查者；自定义 MCP；类似手册的验证循环。
使用 Devin 感觉像一种神奇体验：它能搞清楚工程师从端到端测试角度需要什么，并把 PR 推到终点，达到可供人工审查的程度。 — Luis，工程与数据负责人

备注

Devin 官方客户页。第一方量化：50→170 后端 PR/周；18%→82% 由 Devin 撰写的后端 PR。2–3x / 10→4 周是稳定币的估计，不是已完成的已衡量项目。
