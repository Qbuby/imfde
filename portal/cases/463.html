Lyft 在从单体迁到微服务时保住生产稳定

Sourcegraph 让工程师能重构 API、清技术债，并在 2,000+ 个仓库里核对更新，保证生产稳定，同时加快开发者迭代、支撑持续创新。Lyft 的使命是用世界上最好的交通改善人们的生活。2018 年有超过 30 million 名乘客，Lyft 的生意在长，工程师、仓库和微服务的数量也在长。有效放大并管住一个大工程组织，需要一套精英级开发和实践，保住效率，同时保护和抬升代码质量。「拆解或迁一个服务风险很高，常常涉及几百个仓库的改动，所以准确度要很高。」

给负责人

要解决什么
2018 年公司优先的 PHP 单体 → 微服务拆分（10 年来最大一次重构）：核验每一个调用点/引用，重构无文档 API，删除死代码，且不让 2,000+ 个仓库里的消费者掉队。
结果
核验了跨 2,000+ 个仓库的单体→微服务迁移与弃用；未使用的 API 属性从不同仓库的客户端中移除。页面：显著降低了对生产稳定的风险。无小时数或百分比数字。
接了哪些系统
代码搜索用于在部署新微服务前核验规模化迁移与弃用。
用了什么数据
PHP 单体加上 2,000+ 个仓库 / 微服务。
人还管哪一步
工程师仍自己做重构；搜索用于核验完整性。
多久上线
与 2018 年单体拆分绑定（10 年历史上最大一次）。未给出 Sourcegraph 自身的日历。

给现场的人

主要用在哪
找到一个 API 的所有客户端并移除未使用属性；在 2,000+ 个仓库中搜索/重构对已弃用服务、库和 URL 模式的引用。
以前怎么干
大范围拆分需要在没有正式契约的情况下，跨许多仓库检查无文档 API 的客户端。
卡在哪
数百个仓库中的高风险变更。未使用的属性活在不同仓库里。首次拆分后仍要持续弃用旧系统。
用了什么模型
Sourcegraph 代码搜索（未点名 Cody/LLM）。
怎么验收
定性：生产稳定风险降低；更简单的 API 加快了开发者迭代。无百分比或小时 KPI。
怎么上线
贯穿 2018 年拆分及后续迁移使用。
失败了怎么改
没有正式契约的无文档 API 使得没有跨仓库搜索时很难发现客户端。
能不能复用到下一家
PHP 拆分成功后，同一搜索用于后续弃用。
Lyft 团队不断创新并构建新系统，因此必须拆分并迁离旧系统。Sourcegraph 让我们能在 2000+ 个仓库中搜索并重构对已弃用服务、库、URL 模式等的引用，并有信心没有把任何人落下。——Aneesh Agrawal，Software Engineer，Lyft

备注

Sourcegraph 官方案例（抓取 2026-08-29）。具名 Justin Phillips 和 Aneesh Agrawal。2,000+ 个仓库和 30 million 乘客（2018）在页上。结果为定性（稳定、更简单的 API）。
