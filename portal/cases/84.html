EBANX：从一名工程师的评估到 92% 的已合并 PR

已合并 PR 中 92% 由 Devin 撰写

一项原估六周的关键工程工作流，12 小时完成

Devin 额外贡献了相当于 150 名工程师的产出*

EBANX 是一家全球金融科技公司，总部位于巴西库里蒂巴，专注于新兴市场的跨境和本地支付处理。

EBANX 在拉丁美洲、非洲和亚洲的 20 多个市场处理支付，让国际企业无需设立本地法人实体就能接受数百种本地支付方式。公司增长靠的是进入新市场，而每个新市场都需要对接几十家本地支付提供商，每家都有自己的 API、协议和监管要求。一次对接过去要花工程师团队几周时间去搭建和验证。可进的新市场比能干活的工程师还多，工程产能直接卡住了 EBANX 的扩张速度。

EBANX 打破这个瓶颈的故事，从一名工程师和一项特殊任务开始。

EBANX 的工程副总裁（现任 CTO）Kalecser Kurtz 让 Marlon Brandão de Sousa 别再手写代码，Marlon 当时以为自己要被解雇。

“我说，‘好吧，你要开除我。’他说，‘不是，我们有个叫 Devin 的工具，我想让你测一下。我要你清楚地告诉我，这东西到底能不能帮我们，怎么帮。’”——Marlon Brandão de Sousa

Marlon 负责评估 AI 工具并参与制定工程策略，这份信任来自他二十年职业生涯：他为巴西最大电视网、Itaú 的网上银行平台，以及 EBANX 的全球支付基础设施都搭建过复杂系统。他天生失明，这让他对 AI 工程工具的自主程度格外挑剔。

视力正常的开发者看到语法错误会有红色波浪线，Marlon 却要经历一整套流程：编译、等输出、听屏幕阅读器报错、跳到出错行、修、重新编译、验证。他之前试过的 AI 助手生成的代码错误百出，让他调试时间暴增。

“虽然有语音辅助，但你看不到颜色。没有任何东西帮你把注意力放在该关注的地方。我必须把大脑用到极限，才能在赛道上活下来。”——Marlon Brandão de Sousa

Devin 是第一个能端到端自验的工具。每个 Devin 会话都在一台独立的云机器上运行，里面有 shell、编辑器、浏览器和构建环境。它自主迭代，直到工作达到可合并状态，再返回一个带完整会话轨迹的 PR。

“Devin 会写代码、测试代码、拿到错误、修错误、再测一遍、确保代码能跑、跑 linter，然后开 PR。我再也不用在这些步骤之间手动切换了。”——Marlon Brandão de Sousa

Marlon 花了一个月在真实任务上跑 Devin，逐行研究每条会话的完整日志：它如何推理代码、如何从错误中恢复、如何处理模糊需求。

“我把这些日志读得很仔细，因为我真的想弄懂系统是怎么工作的。那个月结束时，我已经相当确信一场革命要发生了。”——Marlon Brandão de Sousa

为了向全组织证明 Devin 的价值，Marlon 挑了一个对业务至关重要的项目：支付提供商对接——正是拖慢 EBANX 扩张的那类工作。每家新提供商都要实现一组带类型的内部接口、对接外部 API，还要写全套单元测试。

他私下找到负责这个项目的高级开发，说：“如果这东西能行，项目就能在预估时间的 20% 内完成。大家都会问你怎么做到的。如果失败了，你只损失一天，还有剩下的几周可以按正常节奏交付。”——Marlon Brandão de Sousa

团队先写好内部接口的规格，然后把三样东西扔给 Devin：提供商的 API 文档、要实现的接口，以及 EBANX 的内部参考示例。

“我们去喝了杯咖啡。回来时，Devin 已经仔细看过提供商 API 文档，并给出了完整方案：哪个接口对应哪个端点、从文档里 mock 的响应、单元测试，全都有。”——Marlon Brandão de Sousa

原计划六周的项目，Devin 12 小时就搞定了。那位高级开发被说服了，主动把结果拿去组织内分享。

从那以后，EBANX 用 Devin 搭建的基于 SDK 的对接框架，把典型支付提供商对接的交付周期大幅缩短。随着 EBANX 持续在拉丁美洲及更远地区接入新支付提供商，这些时间节省每年都会在几十次对接上叠加。

“我们不再问‘Devin 怎么帮我写得更快’，而是开始问‘我们怎么组织代码，才能让 Devin 真正交付更多’。这个心态转变改变了一切。现在有人给我看优秀结果，我不再要代码，而是要 prompt。”——Bruno Rossetto，EBANX 产品工程总监

第一个项目之后，采用在初级和中级工程师中自然扩散。高级工程师起初持怀疑态度，但 Devin 能像人类 QA 工程师一样自测——在浏览器里启动应用、点击受影响的用户流程、截图验证 UI 元素——最终打动了他们。

Devin 逐渐支撑起 EBANX 最核心的营收系统。最高频的场景是核心支付服务的 API 现代化。对于大型框架迁移，团队会为每个模块、组件或仓库各开一个 Devin 会话，并行完成整个迁移。

Devin 的自动化让它能在后台持续工作：它在核心支付仓库的每个已批准 PR 上起草部署后监控计划，定期做代码审计，分类生产告警，并把诊断结果发回给值班工程师。

Devin 现在是 EBANX 的默认选择。在核心支付平台——EBANX 大部分工程工作落地的平台——92% 的已合并 PR 都是用 Devin 创建的。EBANX 甚至建立了一套“ nudge 系统”：内部审查流程会标记所有非 Devin 编写的 PR，要求工程师说明为什么选择手写代码。

作为支付公司，签名提交、基于角色的访问控制和审计追踪都是硬性要求。过去排查问题要找到原作者问来问去，现在全组织的工程师都能打开 Devin 会话，立即读到每一行背后的思考。

当 CTO Kalecser Kurtz 想了解一项改动时，他会打开背后的 Devin 会话，阅读工作是如何完成的。

“会话留存是最宝贵的产物。”——Kalecser Kurtz，EBANX CTO

Devin Review 又增加了一层信心，它在工程师看到最终 PR 之前自动审查代码。每次部署前，工程师都会参考 Devin Review 的洞见，指导上线后在生产环境里要关注什么。

“它的准确度令人难以置信——几乎像巫术。它找出的每个 bug 往往都是真实存在的，避免了下游更昂贵的修复。这是我用过的最好的审查代理。”——Marlon Brandão de Sousa

EBANX 还投入了保障大量工作安全的防护措施：集成测试、类型安全，以及 linter 强制执行。

给负责人

要解决什么
每个新市场都需要数十个本地支付提供商集成；工程产能制约了 EBANX 扩张速度。
结果
核心支付平台 92% 的已合并 PR 由 Devin 创建。一项预估六周的关键工作流在 12 小时内完成。页面主视觉还写「相当于 150 名工程师的额外工程产出」，脚注：估计基于 Cognition 内部指标——此处不作为客户衡量的 KPI。
接了哪些系统
与 Devin 一起构建的基于 SDK 的集成框架；自动化起草部署后监控计划、运行定期代码审计、分诊告警。工程师看到 PR 之前先有 Devin Review。nudge 系统标记非 Devin 撰写的 PR。
用了什么数据
提供商 API 文档；内部接口；内部参考示例；核心支付仓库；生产告警。
人还管哪一步
工程师在部署前审查 PR 和 Devin Review 见解。产品负责人和工程师在多人 Devin 会话中审查设计文档。
多久上线
一个月评估；首个生产项目约 12 小时，对比六周。

给现场的人

主要用在哪
首个生产环境支付提供商集成（六周预估，约 12 小时交付）；随后是 API 现代化以及核心支付上的并行框架迁移。
以前怎么干
每个提供商集成需要一组工程师花费数周来构建，并对照类型化的内部接口、外部 API 和单元测试进行验证。
卡在哪
市场比工程师多。此前的 AI 助手产出错误百出的代码，使调试时间膨胀，尤其对使用屏幕阅读器的盲人工程师。
用了什么模型
Devin
事情怎么流转
把 Devin 指向文档 + 接口 + 示例；Devin 提出映射、mock、测试。迁移时，每个模块/组件/仓库并行一个会话。Devin 在浏览器中启动应用、点击流程、截取 UI 截图。
怎么验收
为期一个月的日志研究；首个项目对比六周预估；核心支付中已合并 PR 的占比。
怎么上线
从一名工程师扩展到核心支付的默认方式。要求签名提交、RBAC、审计追踪。
失败了怎么改
此前的 AI 助手未能通过屏幕阅读器工作流。资深工程师起初持怀疑态度；被 Devin 像 QA 一样测试自己的工作说服。
能不能复用到下一家
基于 SDK 的提供商集成框架；要求为手工 PR 写明原因的 nudge 系统；作为部署前指导的 Devin Review。
