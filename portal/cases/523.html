给负责人

要解决什么
LLM 对客户来说过于复杂，需要一套可复用的现场交付方法来处理高度模糊的企业 AI 落地
用了什么数据
Phase 3 从客户处取数；Phase 1 用合成数据做原型

给现场的人

以前怎么干
OpenAI 仍有 Solutions Architect（SA）角色：偏顾问性质，很少在客户基础设施上写代码，通常用匿名或离线数据切片做 MVP/PoC
卡在哪
FDE 工作在大量模糊性中，客户在 scoping 阶段描述的东西往往与现场的数据/系统现实不匹配
怎么验收
Phase 2 validation：先问我们 scoping 出来的事是不是能为客户做的最有价值的事，再商定 validation criteria；与用户一起做标注并构建 evals、扩展标注流程、做功能并在 evals 上 hill-climb、最后给出一份 eval 表现相对目标的报告。在交付前先做验证是不寻常的，但有其理由
怎么上线
Phase 3 delivery：驻场客户现场（通常每周数天），搞清问题细节、从客户处取数、通常在 OpenAI 办公室构建方案然后回客户处演示，聚焦能形成端到端方案（或 demo）的最小单元
失败了怎么改
刻意偏向快速验证：尽早撞出 brick walls，再根据不可逾越的约束把范围调整到最有用的事情上
能不能复用到下一家
内部反馈机制：与研究团队双周知识分享会；与产品负责人及 PM 的双周 readout；FDE Field notes Slack 频道（所有 FDE 在内部公开频道分享洞察）；季度 bootcamp（团队分布在 3 大洲 8 个城市）。FDE 团队是 OpenAI Agents SDK 的重要贡献者（SDK 前身是 SA 团队为解决 agent SDK 学习曲线过高而做的 Swarm 框架）
FDE 工作在大量模糊性中，客户在 scoping 阶段描述的东西往往与现场的数据/系统现实不匹配。我们希望偏向快速推进，尽早撞出任何砖墙，再根据不可逾越的约束把范围调整到我们能做的最有用的事情上。
