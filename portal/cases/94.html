Ramp

公司自己讲的数字 · 比较可靠

Devin 修复数万小时技术债，让工程师聚焦最重要的事：为客户省时省钱

Ramp 是一家金融运营平台，帮助公司省时省钱。他们的全平台把企业卡、账单支付、采购、供应商管理、差旅预订、资金管理等功能整合在一起，内置控制和智能，最大化每一美元和每一小时的回报。公司 2019 年成立，是美国增长最快的公司之一，每年为 30,000 多家企业处理数百亿美元的采购。

随着 Ramp 不断扩张新产品，技术待办事项越积越多。日常维护（处理 on-call bug、修坏掉的测试）和清理任务（修 flaky 测试、优化 N+1 查询）很快就把工程师从产品开发上拉开。

经过几次尝试，Ramp 发现一小队熟悉 Devin 的工程师就能省下数万工程师小时，每周合并多达 80 个 PR，横跨整个工程组织。

Ramp 的应用 AI 团队每周用 Devin 解决一项不同的技术债任务，有时直接把工作流嵌入现有的 SDLC。

他们把用 Devin 解决的问题分成三类：

Devin 驱动的内部工具（比如功能开关移除工具）

全自动、事件驱动的任务（比如自动修复 Airflow 错误）

积压任务（比如修几百个慢测试或 flaky 测试）

任何代码库变大，重复的清理工作就会增加，通常占工程师 20% 的时间。测试套件里全是未优化的测试，会直接拖慢开发速度。Ramp 的工程师每天都要在本地跑测试，测试套件每快一分钟，一年就能省下几千小时。

功能开关移除是另一个例子。几百个废弃的功能开关和分叉逻辑让代码变慢、变难读。工程师排查关键 bug 时碰到开关，还得切上下文、查开关管理器、理解代码逻辑，增加大量时间和复杂度。

Ramp 一次用 Devin 解决一个清理或优化任务。他们通过 Devin 的 API 并行触发多个 Devin，批量返回完成的 PR。

一个月内移除 150 个复杂功能开关，省下几千小时工程时间。

“移除一个功能开关可能要好几天。我们以前试过写脚本，但只有 Devin 能彻底移除开关，还能修掉所有影响的测试和其他依赖。上个月光这项就省了 1000 多小时。”

——Rakesh Nori，Ramp 软件工程师

移除单个功能开关就很难，尤其是开关影响代码库里各种格式的逻辑。找出所有死代码路径、条件和边界情况并不直观，耗费宝贵时间。Devin 的核心优势是能跑 Ramp 的测试，确认移除功能开关后核心逻辑没变。有时只有跑测试、看堆栈跟踪才能找出所有下游依赖和受影响的测试，传统静态分析很难做到。

Ramp 因此和 Devin 合作，做了一个低开销、易用的功能开关移除系统：

Ramp 做了一个主 playbook——一个标准提示，可以程序化附加到重复任务上——协调多个“worker” Devin 并行处理功能开关移除的不同部分。这样就能把 playbook 扩展到高复杂度开关，因为任务可以拆分给多个 worker。

一个“clean-up” Devin 检查 worker 输出有没有冲突，再把改动合并成一个容易 review 的 PR。

整个 Devin 工作流被封装成 Ramp 管理后台里的内部工具，任何工程师都能调用。

示例 worker Devin 提示：

You are Worker Devin, responsible for removing the feature flag EXAMPLE_FLAG from the codebase. Perform the following changes on `worker-devin/example-flag-1` Your task: - Remove all instances of the feature flag EXAMPLE_FLAG in the file assigned to you. - The feature flag is now `on` in all cases. Ensure the behavior of the code does not change. - Update any associated tests to reflect the changes. Push your changes to your branch.

现在 Ramp 的工程师只要在内部工具里输入功能开关，Devin 就会在 PR 完成后自动 @ 他。今天 Devin 已经是 Ramp 内部核心工具，能执行以前没有代码代理就做不到的事。

平均 8 分钟从 bug 到 PR。

“让 Devin 先看每一份 Airflow 错误，能省很多时间。有一半情况我们可以直接合并 Devin 的 PR，省下好几个小时调试。即使方案不完美，Devin 的改动也几乎总能把我们更快带到正确解。”

——Peyton McCullough，Ramp 平台工程资深软件工程师

Ramp 的 Data Platform 是很多内部系统和团队的枢纽，跨职能活动和贡献很多，所以经常出问题。每天早上，平台工程团队醒来都要手动调试几条 Airflow 错误或失败报告。这些错误和关键金融服务直接相关，时间敏感，但代码修复本身通常很简单。最大的痛苦在于先得切上下文、定位 bug 位置。

早期实验显示有希望后，Ramp 决定用 Devin 自动处理每一次 Airflow 失败的第一遍，减轻平台工程师压力。实现很简单：Ramp 把 Airflow 错误日志拿来，挑出适合 Devin 修的，然后通过 API 触发 Devin 去修。如果 Devin 的修复通过 CI，它就会开 PR 并 @ 对应工程师。

现在 Ramp 的工程师不用手动调试，只需 review 并批准已经通过 CI 的 Devin PR。即使修复不完全正确，也几乎总在正确方向上，大幅加快修复速度。

给负责人

要解决什么
偿还不断增长的技术债（值班缺陷、损坏/不稳定/缓慢测试、N+1、已弃用功能开关），让工程师能继续做产品执行。
结果
主视觉：每周最多合并 80 个 PR；机械任务每月节省 10,000+ 小时。功能开关：一个月 150 个复杂开关；一名工程师引语：过去一个月在开关上节省超过 1,000 工程小时。Airflow：Devin 从缺陷到 PR 平均 8 分钟；一半时间原样合并。慢测试：套件本地运行时间减少整整一分钟，每名工程师每天最多拿回 20 分钟开发时间。概览：一支很小的精通 Devin 的团队节省了数万工程师小时。
接了哪些系统
用 Devin API 触发并行 worker；内部管理工具；CI 作为合并门禁；验证脚本丢弃失败工作，使 PR 从不会嘈杂。
用了什么数据
代码库；功能开关管理器；Airflow 错误日志；测试套件；未文档化端点。
人还管哪一步
工程师审查/批准 PR。Applied AI 团队选择每周用例。瓶颈是人工审查带宽，不是智能体并行度。
多久上线
功能开关系统：一个月移除 150 个复杂开关。

给现场的人

主要用在哪
功能开关移除 Playbook（worker Devin + cleanup Devin + 管理仪表盘工具）；通过 API 对 Airflow 错误做初过；慢测试拆分和带验证脚本的端点文档。
以前怎么干
机械清理历史上最多占工程时间的 20%。功能开关移除曾尝试脚本化并失败。平台工程师手工调试早晨的 Airflow 错误。
卡在哪
数百个已弃用开关；100+ 个慢测试；500+ 个未文档化端点。测试套件改进一分钟，会在每天数百/数千次运行中放大。
用了什么模型
Devin
事情怎么流转
Playbook 协调 worker Devin 处理文件切片，然后 cleanup Devin 合并成一个 PR。Airflow：过滤说得通的错误 → API 触发 Devin → 若 CI 通过，开 PR 并标记负责人。
怎么验收
已移除开关；节省小时数；Airflow 从缺陷到 PR 的时间；测试套件运行时间；每周已合并 PR。
怎么上线
工作流横向用于整个工程组织；任何工程师都可向内部工具提交开关。
失败了怎么改
脚本化移除功能开关曾经失败。验证脚本之所以存在，是因为有些 Devin 任务无法完成——那些 PR 从不会出现。
能不能复用到下一家
内部功能开关移除工具；每周 Applied AI 接收跟踪器；针对积压类别的 TDD 风格验证脚本。
移除一个功能开关可能要花好几天。我们过去试过脚本化，但只有 Devin 能全面移除功能开关，并修复任何破坏性测试或其他依赖。仅过去一个月，这就为我们节省了超过 1000 工程小时。 — Rakesh Nori，软件工程师，Ramp

备注

Devin 官方客户页。第一方量化：80 个 PR/周；主视觉每月 10,000+ 小时；每月 150 个开关；一个月 1,000+ 开关小时（引语）；Airflow 8 分钟；套件 1 分钟 / 每名工程师每天约 20 分钟。
