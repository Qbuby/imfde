Linktree

公司自己讲的数字 · 比较可靠

Linktree 用 Devin 扩大社交媒体平台覆盖并交付新功能

Linktree 的使命是帮助任何人拥有、发展并变现自己的数字存在。目前有 50M+ 创作者和企业在使用它。

产品看起来简单，但功能丰富，还与数百家合作伙伴集成，帮助用户扩大受众、售卖产品、简化创作流程。

Linktree 团队对 AI 充满信心，认为它能提升速度和价值，因此 Devin 一开放就立刻开始试用。

过去一个月，Devin 提交了约 300 个 PR，合并了约 100 个。大多是修复客户报告的 bug、实现小功能、原型化大功能。

为了支持创作者，Linktree 不断评估要加入哪些新社交平台。最近团队讨论加入 RedNote 和 Lemon8，因为它们最近人气上升。

以前团队需要花时间权衡优先级和取舍。现在直接交给 Devin，跳过冗长的优先级讨论。

加入一个社交平台概念简单，但涉及多个仓库的几个 PR：数据库持久化、URL 解析和验证、更新组件库和 UI 仓库。

Linktree 启动了五个 Devin，每个负责一个仓库和 PR。提示词很简单。

有些仓库需要改动的文件较多，团队用知识功能告诉 Devin 该去哪里找。

团队给 Devin 提供 URL 格式的指导，修复了 SVG 渲染问题，当天就上线了。

Linktree 计划未来做更多类似集成，所以需要进一步简化流程。

团队希望 Devin 能自己组合一系列 PR，而不是手动管理多个 Devin。

和 Cognition 团队讨论后，他们分享了一个 Playbook 脚本，利用 Devin API 自动生成多个 Devin 来实现整个功能，Linktree 立刻就能用。

有些任务 Devin 一次就能搞定，像变魔术。但很多任务它还做不好，关键是团队要培养直觉，知道哪些任务最适合 Devin。

一旦发现某类常见任务效果好，就把它固化下来。比如 Devin 在埋点分析事件追踪上成功率很高。团队把这项工作从所有功能开发中解放出来，不断优化同一提示词。

理解该给 Devin 什么任务有挑战，但 Linktree 团队总结出两点：变更范围、Devin 需要克服的模糊程度。

他们更倾向于把能在几小时内完成的工程师任务交给 Devin，而不是事先过度思考。

Devin 通常能产出一个完整或部分可用的 PR，就算不行，投入的时间也不多。

有时团队让 Devin 尝试新功能，即使知道它可能做不好。它的尝试方案仍能作为有用的概念验证。

最近团队需要在遗留 PHP 后端加一个 cron job，提醒用户社交连接即将过期。由于 PHP 经验有限，团队让 Devin 尝试实现。

这次尝试引发了有用的设计讨论，之后团队给出更具体的指导，完成了修改。

Linktree 给出的使用 Devin 的建议：

指令要简洁具体，避免闲聊。

上下文太长时，考虑在新会话里处理子任务。

一旦发现某类任务效果好，就把它固化下来。

Linktree 对 Devin 的未来充满期待。随着 Devin 和 AI 模型持续改进，很多以前排不上优先级的 bug 和功能，现在团队会先问一句：能不能直接让 Devin 做？

给现场的人

主要用在哪
通过五个并行 Devin（每个仓库/PR 一个）当日完成 RedNote/Lemon8 支持；把分析事件埋点操作化；PHP cron 概念验证。
以前怎么干
增加一个社交平台意味着跨仓库的多个 PR（数据库持久化、URL 解析/校验、组件库、UI）。团队在接手工作前争论优先级。
卡在哪
有限的 PHP 专长使遗留后端中 cron 任务的范围界定耗时。分析事件追踪是每个功能上的显著工作量。
用了什么模型
Devin
事情怎么流转
跨仓库变更为五个并行会话。Knowledge 功能教授文件位置。Playbook 后来自动生成多个 Devin。
怎么验收
过去一个月撰写 vs 合并的 PR；分析埋点成功率。
怎么上线
工程团队；在优先级争论前问「能不能直接 Devin 一下？」
失败了怎么改
Devin 在许多任务上吃力；团队学会优先选择工程师几小时能完成的工作。长上下文：在子任务上开新会话。PHP cron 首次尝试吃力，变成设计讨论。
能不能复用到下一家
通过 Devin API 的 Playbook 用于多 PR 功能；在功能工作中复用经打磨的分析事件提示。
