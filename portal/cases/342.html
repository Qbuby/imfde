Indeed 保持代码更新，并加快开发速度

Indeed 把大规模代码更新所需的手工量砍了 90%，每年省下数千个工程小时，跨团队协作更好了，全球代码库里那些看不见的生产力障碍也清掉了。Indeed 是一家跨国求职网站，员工超过 11,000 人，工程师大约 2,000 人。求职搜索功能覆盖 28 种语言、60 个国家。

找出并修好有问题的代码。Indeed 的开发常常要删掉或更新某种代码模式、某个库，这些东西会散落在整份代码库、分属不同团队。要改，得先找出每一处，再跟相关团队打招呼，请他们动手。

给负责人

要解决什么
跨团队找到每一个库或代码模式实例，让负责人去更新（尤其是漏洞/隐私），并停止把看不见的工作塞进产品团队。
结果
页头：大规模代码更新的手工投入减少 90%，每年节省数千工程小时。Hodge：花 10 分钟做代码审查，对照接下来六小时做这个变更。每个合并的自动化合并请求约节省 1 小时（粗略保守估计）；一年几千个自动化合并会节省若干员工量级的时间。
接了哪些系统
Universal Code Search + Batch Changes；服务负责人审查生成的 MR。从搜索生成 JIRA 只是原型。
用了什么数据
全球多团队代码库（实例被描述为五个或 500 个）。
人还管哪一步
服务负责人仍审查自动化合并请求（页上：10 分钟审查对照做变更的六小时）。

给现场的人

主要用在哪
带搜索链接的更新请求；Batch Changes 做组织范围库更新；退役残留技术；改善构建时间的构建系统替换（定性）。
以前怎么干
向产品与工程群发邮件（「赶猫」）。内部平台团队看不到一次请求是 5 还是 500 个实例。Jared Hodge 在 Batch Changes 出现前做出了从搜索生成 JIRA 的原型。
卡在哪
少数人从不行动。平台团队没有权力把变更做完。隐性速度税（为极小用户份额保活旧技术；构建系统残留）。
用了什么模型
Sourcegraph Universal Code Search + Batch Changes（未点名 Cody/LLM）。
怎么验收
Hodge 的保守估计：每个落地的自动化合并约节省 1 小时。「一年几千个自动化合并」→「相当于若干员工的时间。」
怎么上线
由 Developer Experience / 内部平台在约 2,000 名工程师中使用。
失败了怎么改
邮件群发让工作做不完。单靠搜索能识别工作，但直到 Batch Changes 才能完成它。
如果我能把产品团队必须做的工作量减少 90%，那就是巨大胜利。他们不仅要做的更少——我们是请他们花 10 分钟做代码审查，而不是花接下来六小时做这个变更。——Jared Hodge，Senior Manager，Developer Experience

备注

Sourcegraph 官方案例（抓取 2026-08-29）。具名 Jared Hodge。90% 与 10 分钟对 6 小时是 Hodge 引言；导语也说「每年数千工程小时」。约 1 小时/MR 明确是粗略保守估计；「几千」MR/年是条件句（「如果我们在做」）。11,000 名员工 / 2,000 名工程师是公司规模。
