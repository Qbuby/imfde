Workiva 把大规模改代码的时间砍了 80%

Workiva 用 Batch Changes 换掉内部工具后，拿到一套维护得好、功能齐全的方案，更新更顺、采用也更好，团队可以把精力放到创新上，而不是养工具。

还技术债。Workiva 的 Client Platform 团队负责开发和维护所有产品都依赖的框架和共享库，包括一套共享 UI 组件库，以及几十个 Dart 包，撑住整个工程团队。每次给某个包装一次版，还得把改动铺到其他团队用的 70+ 个仓库，免得破坏性变更。他们自己做过内部自动化工具，但要持续维护，也看不到从头到尾的完成路径。

给负责人

要解决什么
把框架与共享库发布传播到 70+ 仓库，而不维护内部自动化工具，也不让组织停下来做一个迭代/季度的技术债清理。
结果
Batch Changes 把大规模代码变更所需时间对照手工减少 80%。用于所列更新类别的 70+ 仓库。
接了哪些系统
Batch Changes 步骤经 Docker 运行，使现有工具能以最小投入被纳入。
用了什么数据
70+ 前端/产品仓库；几十个 Dart 包；共享 UI 组件库。
人还管哪一步
团队仍运行并审查批量变更；对照旧内部工具，对完成路径有可见性。

给现场的人

主要用在哪
传播新 React 版本；更新 Kubernetes API 版本；CDN 迁移 + 所有代码引用；新语言版本的 Dart UI 组件语法；在新 Chrome 发布前测试批量变更。
以前怎么干
内部工具自动化多仓库更新；需要持续维护且缺乏端到端可见性。替代方案：跨几十个仓库手工编辑或把更新压进待办。
卡在哪
技术债积到工作停一个月、一个迭代或一个季度。破坏性变更发布被工具痛苦卡住。
用了什么模型
Sourcegraph Batch Changes（未点名 Cody/LLM）。
怎么验收
对照手工做同样大规模变更的时间：减少 80%（页面，在标题/英雄/正文中重复）。
怎么上线
Client Platform 今后将使用 Batch Changes，而不是维护内部工具。
失败了怎么改
内部自动化工具需要持续维护，且不显示完成路径。习惯让技术债堆到停工。
能不能复用到下一家
永久替换内部工具（「今后」）。
使用不是我们维护的工具节省我们的时间并推动更好的采用。对照我们内部建的工具，它更好用、功能更完整、文档更好。——Evan Weible，Workiva Staff Software Engineer

备注

Sourcegraph 官方案例（抓取 2026-08-29）。具名 Trent Grover、Evan Weible、Joe Bingham。80% 是页面对照手工大规模变更的陈述比较。70+ 仓库是爆炸半径，不是结果。
